## 0. 先讀這一段（整份文件的地圖）

近幾個月，佈局相關的能力很多是以「**純函式**」或「**store 動作**」交進倉庫的：畫面上不一定看得到按鈕，但 L2（畫布互動層）之後都要呼叫它們。

**L1 契約實驗室**就是一張「說明＋可按的實驗臺」（V19 起也當 **Hub**：頁內有入門／詞彙／目錄）：

1. 用表格寫清：這個函式是幹嘛的、誰該呼叫、最常見的錯誤用法  
2. 提供一鍵案例：真的呼叫程式，把結果用 JSON 印出來  
3. （頁內）最短路徑教學、精簡詞彙、長期 API inventory（已列／待列）

它**不是**正式遊戲畫面。W1018 公開驗收 V2 請以 [ACCEPTANCE](./ACCEPTANCE_V2_c5_chain.md) 為準；W1026 的 tutorial／Lab 驗收（WEEK V2）以 lab 頁可跟做為準。Lab 的價值是：**降低串接成本、減少猜 API**。

## 2. 詞彙表（專有名詞白話）

閱讀後文時，若出現左側詞，請用右側理解。函式名稱維持英文，方便對程式搜尋。

| 標記詞 | 白話說明 |
|--------|----------|
| **L1** | 基礎層：資料、規則函式、store 動作。通常**不**直接畫正式 UI。 |
| **L2** | 互動層：畫布上拖設備、拉管線、點選等。應**呼叫** L1，而不是自己重寫一套規則。 |
| **契約** | 「呼叫端與提供端都同意的用法」：輸入什麼、輸出什麼、什麼不能做。 |
| **純函式** | 同一個輸入大致得到同一個輸出、不偷偷改全域畫面狀態的函式（方便測試）。 |
| **store** | 前端集中存放狀態的地方（本專案用 Pinia）。例如 `layoutStore` 管佈局上的設備。 |
| **佈局／layout** | 玩家在格線上放了哪些設備、管線怎麼走、誰連誰。 |
| **設備（device）** | 畫布上的一台機器實例；有自己的 `id`（uid）。 |
| **機型（machineType）** | 這台設備是哪一種機器。**新模型用英文 id**（如 `crusher`），不是中文顯示名。 |
| **埠（port）** | 機器邊上的進料／出料接口；拉管線時要對準埠，而不是點機殼任意處。 |
| **PortRef** | 「連到哪一台的哪一個埠」的身分證：`{ deviceId, portType, portIndex }`。語意以它為準，不要事後用座標反推。 |
| **portIndex** | 該機型當前模式下，`input_ports`／`output_ports` 陣列的 **0-based** 第幾個（正上三埠由左到右常是 0、1、2）。 |
| **offset（資料欄）** | 埠在某一邊上的格偏移（從左／上起算）；與 `portIndex` 不同：前者是幾何位置，後者是陣列序。 |
| **埠熱區** | 滑鼠附近「算有點到這個埠」的寬容範圍（不是無限小的一個數學點）。對應函式：`hitTestPortAt`。 |
| **外側錨點格** | 設備佔格**之外**相鄰的那一格，專門給連線規則／路徑端點對齊用（`resolvePortAnchorCell`）。**不是**滑鼠點擊的主依據。 |
| **埠視覺邊心** | 畫在設備**邊線中點**上的幾何點（`portPointOnMachine`）；熱區圓心也在這裡。 |
| **佔格** | 一台設備在格線上佔了哪些格子；用來判斷重疊、出界。 |
| **基地／base region** | 允許蓋建築的範圍；超出時可能要畫紅框警示。 |
| **管線／pipeline** | 傳送帶或管道在地上的路徑（常由轉折點 waypoints 組成）。 |
| **連線／connection** | 「哪一台的哪個埠」接到「另一台的哪個埠」，並綁定某條管線。 |
| **媒質／media** | 這條線傳固體（belt）還是流體（pipe）等；連錯媒質會失敗。 |
| **源／source** | 產線起點：自己產生物料，而不是靠上游餵入。 |
| **sink** | 產線終點：接收物料（如物品輸入口）。 |
| **拓樸／topology** | 把設備當「點」、管線當「邊」的關係圖；引擎靠這張圖算流量。 |
| **流量／rate** | 每分鐘通過多少個物料（單位：個／分鐘）。 |
| **primaryOutput** | 源設備「主要產出哪種材料」的欄位名。 |
| **操作歷史／history** | Undo／Redo 用的堆疊；亂寫進歷史會讓 Ctrl+Z 行為怪異。 |
| **fixture／示範快照** | 開發用預先做好的範例佈局；**不應**在正式頁開場自動載入（#58）。 |
| **draft** | 尚未寫入 store 的「預覽中」狀態（例如拖著還沒放下的設備或線）。 |

## 4. V14｜放置與連線（能不能放、能不能連）

### 4.1 `canPlaceDevice`

| 項目 | 說明 |
|------|------|
| **用途** | 問：「若現在把某機型以某個位置／旋轉放下去，合不合法？」 |
| **目的** | 讓**預覽**（還沒寫入）和 **`layoutStore.addDevice`（真的寫入）** 用同一套規則，避免「影子說 OK、真放卻爆」。 |
| **誰該呼叫** | 工具列意圖、落子預覽、以及 store 內部放置路徑。 |
| **串接方式** | L2 拖曳或點格預覽時呼叫；根據回傳的結果決定要不要畫綠／紅預覽。不要自己另外 `import` 重疊偵測函式重算一遍當預覽。 |
| **常見誤用** | 自己算佔格重疊來當預覽 → 規則一改，預覽與真放又分裂。 |

### 4.2 `canMoveDevice`

| 項目 | 說明 |
|------|------|
| **用途** | 問：「已經在場上的某一台，移到新格子合不合法？」 |
| **目的** | 移動與「新放一台」規則相近但不完全相同（例如原位應永遠合法）。 |
| **誰該呼叫** | 拖曳預覽、放開前確認。 |
| **串接方式** | 拖設備時用**這支**；不要把「移動」假裝成「用 `canPlaceDevice` 新放一台」而忽略原設備佔格。 |
| **常見誤用** | 移動時誤呼叫 `canPlaceDevice` → 可能把自己舊位置也當成障礙。 |

### 4.3 `canConnect`

| 項目 | 說明 |
|------|------|
| **用途** | 問：「這條管線路徑（waypoints）能不能在兩端接到合法的埠？」 |
| **目的** | 與解析連線時用的錨點規則一致，避免「畫面上連得上、存檔後變斷線」。 |
| **誰該呼叫** | 拉線 draft、以及 `addPipeline` 前的防線。 |
| **串接方式** | C1／L2 在放開滑鼠準備建管線前呼叫；失敗時可搭配下一支把原因講成人話。 |
| **常見誤用** | 自己寫「端點碰到哪個埠」的私規；或只檢查一端命中、不管方向／媒質。 |

### 4.4 `describeConnectFailure`

| 項目 | 說明 |
|------|------|
| **用途** | 把 `canConnect` 的結構化失敗結果，轉成給人看的句子。 |
| **目的** | **規則層保持乾淨**（只回代碼／結構），UI 文案集中在這一支。 |
| **誰該呼叫** | 需要提示玩家／開發者的 UI。 |
| **串接方式** | 先拿 `canConnect` 結果 → 若失敗再呼叫本函式顯示。 |
| **常見誤用** | 在 L1 規則函式裡直接拼一長串 UI 字串 → 難測試、難重用。 |

**V14 更深演示（可選）：** `/dev/placement-connect-check.html`（綠／紅案例卡）。

## 5. V15｜出界與埠熱區

### 5.1 `devicesOutsideBase`

| 項目 | 說明 |
|------|------|
| **用途** | 列出「佔格超出基地範圍」的設備 id。 |
| **目的** | 給畫布畫紅框／警示；**預設不當成「禁止放置」的唯一理由**（除非產品之後改裁決）。 |
| **誰該呼叫** | 畫布警示層、驗證視覺。 |
| **串接方式** | 讀完 list 後只做顯示；不要擅自把它塞進 `canPlaceDevice` 的拒絕理由（除非主編改規則並改契約）。 |
| **常見誤用** | 把「出界」與「重疊不合法」混成同一種 Placement 失敗。 |

### 5.2 `hitTestPortAt`（**埠熱區**命中）

| 項目 | 說明 |
|------|------|
| **用途** | 給一個連續座標（滑鼠在格線上的位置），問「現在算點到哪個埠？」。 |
| **目的** | 讓拉管線好點：埠周圍有一塊寬容的**熱區**（預設大約 0.5 格半徑），不必像素級對準。 |
| **誰該呼叫** | C1／L2：開始拖線、拖曳中更新目標、放開接線。 |
| **串接方式** | 滑鼠事件 → 轉成佈局座標 → `hitTestPortAt` → 得到 **PortRef**（含 `deviceId`、`portIndex`）與 `side`／`media` → **存進 draft**。 |
| **常見誤用** | 拿 **`findPortAt`**（偏「格點上精確查詢」）硬當滑鼠熱區 → 手感極差、與 C1 設計不符。 |

> **對照記憶：**  
> - `hitTestPortAt`＝給**手指／滑鼠**用的「附近有沒有埠」（圓心＝**埠視覺邊心**）。  
> - `findPortAt`＝給**演算法／格點**用的精確查詢（對的是**外側錨點格**）。兩者不要互當。

### 5.3 埠幾何與 L2 串接（週會／toby FAQ）

#### 兩套座標，用途不同

以 **3×3** 設備、左上角在 `(ox, oy)`、正上三個 in 埠（`offset` 0／1／2）為例：

| 用途 | 函式 | 正上「中間埠」（offset＝1）落點 |
|------|------|--------------------------------|
| **視覺／滑鼠熱區** | `portPointOnMachine`＋`hitTestPortAt` | 設備**頂邊**中點：`(ox+1.5, oy)` |
| **連線錨點／canConnect** | `resolvePortAnchorCell`＋`findPortAt` | 佔格**外一格**：`(ox+1, oy-1)` |

```text
        [外錨0] [外錨1] [外錨2]          ← y = oy-1（給規則／路徑端點）
           ↓       ↓       ↓
        ┌──────┬──────┬──────┐
        │      │ ▲邊心│      │          ← y = oy；中埠視覺點 x=ox+1.5
        │      │(埠1) │      │
        └──────┴──────┴──────┘          ← 3×3 佔格
```

為什麼要外一格？若管線端點落在設備自己的佔格裡，每條線都會跟來源／目標設備「同格」，碰撞判定會全面誤報。因此錨點刻意推到外側。

### 5.3 `resolveConnections`／waypoints（V20 可點測）

| 項目 | 說明 |
|------|------|
| **`resolveConnections`** | 管線 waypoints **首／末格**對外側錨點 → `Connection`；對不上則該側 `null`（斷線，管線不刪）。**不做**媒質檢查（那是 `canConnect`）。 |
| **`buildConnectionWaypoints`** | 兩外側錨點 → 直線或**單轉角**；不驗媒質／碰撞。 |
| **`buildGapConnectionWaypoints`** | 兩設備間**固定中央通道** → **雙轉角**；無通道回 `null`。不是通用繞障搜尋；結果仍須 `canConnect`。 |

lab V15 分頁有一鍵對照。

#### L2／L3 會不會「自動知道」是第幾個埠、哪一台機？

| 層 | 會不會知道 |
|----|------------|
| **L1** | 算得出並**回傳**（例如 `hitTestPortAt` 帶 `deviceId`＋`portIndex`）。 |
| **L2** | **呼叫後就知道**：必須把回傳的 **PortRef 存進 draft**，整條線語意跟這份走。不是接上 API 就隱形同步。 |
| **L3** | **通常不直接查 L1**；由 L2 把「畫在哪、高亮誰」做成 props。 |

「從正上第 2 個埠拉線」在語意上＝draft 裡 `portIndex === 1`（若陣列由左到右是 0、1、2）。畫線起點可用邊心好看；**不要**只靠「線看起來從外格中間出來」事後反推是第幾個埠。

#### 兩台機器的外側錨點撞同一格時，來源是哪台？

1. **起拖請用 `hitTestPortAt`**（比的是各埠**視覺邊心**到滑鼠的距離）。兩台外錨同格時，邊上圓心多半仍不同 → 較近者勝 → 回傳的 **`deviceId`** 就是來源機。  
2. 幾乎一樣近時：先看你傳的 **`prefer`**（開始拖建議 `'output'`，放開建議 `'input'`）；仍平手則取展開掃描序較前者。  
3. **不要**只用外錨格呼叫 `findPortAt` 當起拖：同格多埠時更容易選錯機。`findPortAt` 留給 `canConnect`／解析連線。

建議起拖程式節奏：

```text
pointerdown 靠近埠
  → hitTestPortAt(point, devices, undefined, { prefer: 'output' })
  → 若有結果：draft.from = 該 PortRef（含 deviceId、portIndex）
  → 畫線：起點可用 portPointOnMachine（邊心）；語意只認 PortRef
pointerup
  → hitTestPortAt(..., { prefer: 'input' }) 得 draft.to
  → canConnect／addPipeline（規則側對外錨；身分仍用同一套 PortRef）
```

## 6. V16｜源素材寫入、旋轉與拓樸映射（本週 V2 核心）

### 6.1 `setDevicePrimaryOutput`

| 項目 | 說明 |
|------|------|
| **用途** | 設定（或清除）某台設備的 `primaryOutput` 與可選的每分鐘速率。 |
| **目的** | 讓「源要產什麼」有**唯一寫入點**，並進入操作歷史（可 Undo）。 |
| **誰該呼叫** | 日後左面板／表單；目前以測試與 lab 案例為主。 |
| **串接方式** | `layoutStore.setDevicePrimaryOutput(uid, itemId, ratePerMin?)`；`itemId === null` 清除；省略速率＝**30**。 |
| **常見誤用** | 同時改舊的 `editorStore` 欄位（**雙寫**）→ 違反主編裁決，Undo／引擎會對不起來。 |

### 6.2 `rotateDevice`

| 項目 | 說明 |
|------|------|
| **用途** | 設定單一已放置設備的 `rotation`（0–3）。 |
| **目的** | L1 唯一旋轉寫入點；自動進 `MachineRotation` 歷史；**原點與既有管線座標不動**。 |
| **誰該呼叫** | L2 快捷鍵／工具列旋轉（#78 應改呼叫此 action，勿自寫第二套）。 |
| **串接方式** | `layoutStore.rotateDevice(uid, rotation)`；同角度＝no-op 且不進歷史。 |
| **重疊** | 與 `addDevice`／`moveDevice` 相同：**不擋寫入**；E001 由 `layoutIssues`／驗證標出。 |
| **常見誤用** | 旋轉時改 `position` 或改寫管線 waypoints；或把預檢 `overlap` 當寫入擋板。 |

### 6.3 `addPipeline`／`removePipeline`（V20 可點測）

| 項目 | 說明 |
|------|------|
| **用途** | 寫入／刪除管線；`addPipeline` **內含** `canConnect`（失敗→`invalid`），成功進歷史。 |
| **誰該呼叫** | L2 確認拉線／刪線；勿在 L2 自寫第二套連線防線。 |
| **常見誤用** | 略過 `canConnect`；端點用熱區連續座標而非外側錨點整數格。 |

lab V16 分頁有獨立 Pinia 一鍵案例。

### 6.4 `toTopology`

| 項目 | 說明 |
|------|------|
| **用途** | 輸入設備、管線、連線列表，輸出引擎用的節點（nodes）與邊（edges）。 |
| **目的** | 當**轉接器（adapter）**：佈局模型不必等於引擎內部模型。 |
| **誰該呼叫** | 任何要把正式佈局餵給流量引擎的路徑；#74 的驗收測試也走這裡。 |
| **串接方式** | 從 `layoutStore`（或同等快照）取出 devices／pipelines／connections → `toTopology` → 再交給建圖／傳播流量。 |
| **常見誤用** | 以為引擎會**自動 watch** `layoutStore` 而什麼都不用轉；目前約定是**經 `toTopology`**。 |

**V16 補充頁（可選）：** `/dev/layout-store-preview.html`。

## 7. V17｜機型查表、引擎切片、歷史隔離

### 7.1 `resolveMachineDef`

| 項目 | 說明 |
|------|------|
| **用途** | 用機型字串查機器定義：優先當**英文 id**查，找不到再試**中文名**（過渡期）。 |
| **目的** | 新佈局存英文 id，舊資料／舊頁可能仍是中文名；統一入口避免「全查無」。 |
| **誰該呼叫** | 驗證、引擎、以及任何新程式要查機型定義時。 |
| **串接方式** | 先 `resolveMachineDef(machineType)` 得到定義物件，再取其 `.name` 等欄位往下用。 |
| **常見誤用** | 新碼直接只呼叫只認中文名的舊查表，當唯一權威。 |

### 7.2 `getRecipesForMachine(def.name, mode)`

| 項目 | 說明 |
|------|------|
| **用途** | 依「機器的中文名＋模式」取配方列表。 |
| **目的** | 配方資料表的鍵仍是**中文名**；即使機型 id 英文化，配方鍵尚未整表搬家。 |
| **誰該呼叫** | 驗證／引擎在 **resolve 成功之後**。 |
| **串接方式** | `const def = resolveMachineDef(...)` → `getRecipesForMachine(def.name, modeId)`。 |
| **常見誤用** | `getRecipesForMachine('crusher')` 把英文 id 當配方鍵 → 取到空。 |

### 7.3 引擎鏈：`toTopology` → 建圖 → 傳播流量

| 項目 | 說明 |
|------|------|
| **用途** | 在英文 id 快照上算出產線流量（驗收釘死：**源礦／加工／sink 各約 30／min**）。 |
| **目的** | 證明 C5「寫得進、也讀得出」的最小切片，而不必先做完整右側產耗 UI。 |
| **誰該呼叫** | 單元測試、未來正式掛載；lab 內有一鍵案例可觀摩。 |
| **串接方式** | 見 [ACCEPTANCE §3](./ACCEPTANCE_V2_c5_chain.md)；細節函式名含 `buildGraph`、`propagateFlows` 等，屬引擎內部步驟。 |
| **常見誤用** | 正式頁開場自動載入示範快照並當「真玩家進度」（已廢，見下）。 |

### 7.4 歷史情境：`historyContext`／切換頁面時清空

| 項目 | 說明 |
|------|------|
| **用途** | 分辨你現在在「正式頁」還是「／dev」；跨這兩種情境時清空 Undo 堆疊。 |
| **目的** | 避免在開發頁按的 Ctrl+Z，切回正式頁卻撤到另一套操作。 |
| **誰該呼叫** | 已掛在路由器；一般畫面作者**不必**自己再清一次。 |
| **串接方式** | 新開的獨立 HTML 演示若自帶一套 Pinia，本來就與主 SPA 分開，不要假設它們共用歷史。 |
| **常見誤用** | 依賴正式頁自動 `loadSnapshot(connected)` 當開場；或以為所有 `/dev` HTML 都與主站共用同一個歷史堆疊。 |

**V17 補充頁（可選）：** `/dev/flow-engine`（舊模型演示較多；**佈局英文 id 產線請以測試／本 lab 的 V17 案例為準**）。

## 8. 串接硬規則（請貼在 PR／碼評）

1. **預覽與真放同一規則** — 放置／移動／連線走 V14 契約，不私建第二套。  
2. **滑鼠點埠用埠熱區** — `hitTestPortAt`，不是 `findPortAt`；規則／衍生連線用外側錨＋`resolveConnections`。  
3. **拉線語意帶 PortRef** — 起拖存 `deviceId`＋`portIndex`；外錨同格也不改用「猜格」；間隙路徑用 `buildGapConnectionWaypoints`，仍須 `canConnect`／`addPipeline`。  
4. **源素材只寫 layoutStore** — `setDevicePrimaryOutput`；禁止雙寫 `editorStore`。  
5. **旋轉只寫 layoutStore.rotateDevice** — 原點／管線座標不動；勿在 L2 自寫第二套。  
6. **重疊（E001）不擋寫入** — `addDevice`／`moveDevice`／`rotateDevice` 遇重疊仍寫入；預檢 `can*` 仍可回 overlap。  
7. **引擎讀佈局要經 toTopology** — 不要假設自動監聽。  
8. **查機型用 resolveMachineDef；查配方用 def.name** — 英文 id ≠ 配方鍵。  
9. **正式頁不自動載示範佈局** — 示範留給 lab／dev；lab 寫入案例用**獨立 Pinia**，不污染正式頁 store。  
10. **改契約文案** — 優先改 `contractCatalog.ts`，再考慮是否同步本檔。
