**所屬層次：** L1（最底層）
**對應專案：** Endfield Playground（明日方舟：終末地 集成工業模擬器）
**文件版本：** v0.1

---

## 1. 層級定位

L1 是整個前端架構的「資料 + 規則」底盤。所有 Pinia store、共用型別、純函式工具、FlowEngine 計算核心、history 命令佇列、graph utility 都住在這一層。L1 對外只暴露：

- **型別**（TypeScript interface / type）
- **stores 的 actions / getters**
- **純函式 utility**（graph、detector、helper）

L1 不關心畫面長什麼樣、互動怎麼觸發、樣式是 Tailwind 還是 Nuxt UI。

### 不做什麼（重要）

| 不做 | 理由 |
|---|---|
| 不寫真實 UI 元件 | UI 是 L2/L3 的責任。L1 只允許開發期用的 debug 測試頁 |
| 不直接綁定快捷鍵 | 快捷鍵是互動，屬於 L2 容器層 |
| 不寫 Tailwind class、不調樣式 | 樣式屬於 L3 |
| 不直接讀 DOM、不操作 canvas 渲染 | 那是 L2 容器或畫布層的事 |
| 不存「視圖狀態」（hover、drag 預覽座標的純視覺部分） | 視覺暫態原則上留在 L2，除非 spec 明確要求進 store |

## 2. 三層架構與三條硬規則

整個專案分三層：

```
L1 基礎層   : Pinia stores、型別、FlowEngine、history、graph utility
L2 容器層   : 消費 store、主畫面 layout、互動（拖拉/快捷鍵/框選），對下層提供 props/events
L3 UI 元件層 : 純展示元件，不 import 任何 store，只看 props 發 events
```

### 三條硬規則（L1 視角）

1. **L3 禁止 `import { useXxxStore }`** — L1 設計 store 介面時，必須讓 L2 能透過 props 把資料攤平餵給 L3。
2. **L1 不寫真實 UI** — 只能寫 dev-only debug 頁（例如 `/dev/flow-engine-test`），不能塞進 production bundle 的 UI route。
3. **L2 不做純視覺樣式調整** — 反過來提醒 L1：actions 不要回傳「樣式建議」之類的東西，只回傳資料事實。

## 5. L1 對 L2 的交付清單（解鎖下游）

下游 L2 容器層要能開工，L1 必須先穩定下面這些介面：

### 5.1 型別交付（實際路徑與簽名）

```typescript
// src/types/graph.ts
//   ↑ 採 Vue Flow 慣例：節點稱 FactoryNode、邊稱 FactoryEdge
export interface FactoryNode {
  id: string
  type: string                    // Vue Flow node type
  position: { x: number; y: number }
  data: FactoryNodeData
}

export interface FactoryNodeData {
  label: string
  machineType: string
  recipeIndex: number
  rotation: Rotation              // 0 | 1 | 2 | 3（90 度為單位）
}

export interface FactoryEdge {
  id: string
  source: string                  // FactoryNode.id
  target: string
  sourceHandle?: string           // port id
  targetHandle?: string
}

// src/types/editor.ts
export type Rotation = 0 | 1 | 2 | 3
export type ToolMode = ...
export type EquipmentType = ...

// src/types/validation.ts
export type AlertLevel = 'error' | 'warning'

export interface Alert {
  uid: string
  level: AlertLevel
  code: string
  message: string
  relatedDeviceUids: string[]
  relatedConnectionUids: string[]
}

export interface ValidationContext {
  devices: FactoryNode[]
  connections: FactoryEdge[]
  getDef: (machineType: string) => Machine | undefined
  // 不含 graph —— Phase 1 detector 均不需要 graph topology
}

export interface Detector {
  code: string
  level: AlertLevel
  run: (ctx: ValidationContext) => Alert[]
}
```

### 5.2 高階 Actions 簽名

L1 必須提供「一次操作完成所有副作用」的高階 action 給 L2 直接呼叫，**L2 完全不需要自己包 Command**。每個 high-level action 內部負責：
1. 執行 mutation
2. 同時把對應 Command 推入 `historyStore` 的 undo stack

```typescript
// useEditorStore（兼任 placedDevice + pipeline）
placeDevice(node: FactoryNode): void
moveDevices(ids: string[], delta: { x: number; y: number }): void
rotateDevice(id: string, rotation: Rotation): void
removeDevices(ids: string[]): void
setRecipe(id: string, recipeIndex: number): void
pasteSelection(nodes: FactoryNode[], edges: FactoryEdge[], offset: { x: number; y: number }): void
addConnection(edge: FactoryEdge): void
// ↑ 內部包含 autoNode 自動產生邏輯：物流橋於 Phase 1 隨管線繪製自動插入；
//   分流器 / 匯流器自動生成屬 Phase 2，同樣以 createMacroCommand 在內部組合並推入歷史
removeConnection(edgeId: string): void

// 上述 8 個高階 action 皆於內部自動產生 Command 並推入 historyStore，
// L2 完全不需要也不應該自己呼叫 historyStore.execute()
```

### 5.3 共用 Utility

```typescript
// src/composables/useFlowEngine.ts —— graph + FlowEngine 演算法集中於此
// （經評估後不另抽 src/lib/graph/，理由見 aaaaa.md §3.2）
export function buildGraph(
  nodes: FactoryNode[],
  edges: FactoryEdge[]
): FlowGraph

export function topologicalSort(graph: FlowGraph): string[]
// 註：環路偵測直接寫入 graph.hasCycle 與 graph.invalidSubgraphUids

// src/lib/history/createMacroCommand.ts
// 注意：createMacroCommand 為 L1 內部使用 helper（例如 addConnection 需要組合
// placedDevice 與 pipeline 的 mutation）。L2 不應直接呼叫。
export function createMacroCommand(label: string, cmds: Command[]): Command
```

### 5.4 使用範例（給 L2 看的）

```typescript
// L2 容器層的呼叫模式
const editorStore = useEditorStore()
const historyStore = useHistoryStore()

// 拖出管線完成 → 一行 call，L1 action 內部自動產生 Command 並推入歷史
editorStore.addConnection(edge)

// L2 仍然可以（且應該）直接呼叫 undo / redo
historyStore.undo()
historyStore.redo()
```

L2 不需要知道 autoNode 怎麼產、不需要自己包 Command、不需要自己呼叫 `historyStore.execute()`。L2 只負責呼叫 high-level action 與觸發 undo / redo；Command 的產生與入棧完全由 L1 store action 內部處理。

## 6. 與其他層的協作流程

### 6.1 介面變更流程

L1 actions 簽名 / 型別屬於對外 API。變更時：

1. Architect 在 PR 描述中標註 **「Breaking: L2 interface change」**
2. 同步知會 L2 主責人（待人員到位）
3. 合併後同步更新本資料夾下的職責文件

### 6.2 PR Review 規則

| 變更類型 | 必經 review |
|---|---|
| 新增 / 修改全域型別 | dernoson + aaaaa 任一 |
| FlowEngine / graph utility | aaaaa 主審 |
| historyStore 本體 / L1 store action 的 Command 包裝規範 | dernoson 主審 |
| 新增 detector | aaaaa 或 dernoson 任一（檢查介面遵循） |

### 6.3 PR 邊界檢查

審核時務必確認：

- L1 PR **不可包含** `.vue` 元件、`<template>`、Tailwind class
- L1 PR **不可** `import` 任何 L2 / L3 路徑
- L1 PR 必須有對應單元測試（utility / detector / store actions）
