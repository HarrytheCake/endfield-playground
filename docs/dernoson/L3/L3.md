# L3 UI 元件層 — 總覽

**所屬層次：** L3（最上層／純展示）
**對應專案：** Endfield Playground（明日方舟：終末地 集成工業模擬器）
**文件版本：** v0.1

---

## 1. 層級定位

L3 是整個前端架構的「畫面」層。所有看得到的元件——左側面板、下方工具列、右側統計、Flow Chart 節點、視角切換按鈕——只要它是「純展示／受控元件」，都住在這一層。

L3 對外只有兩種介面：

- **Props**：上游（L2）餵進來的純資料與狀態 flag
- **Emits**：使用者操作後 emit 出去的 event，由 L2 決定後續行為

L3 不知道 store 存在、不知道資料從哪來，理論上每個元件都能在 Storybook 或獨立預覽頁中以 mock data 完整呈現。

### 不做什麼（重要）

| 不做 | 理由 |
|---|---|
| 不 `import { useXxxStore }` | 違反就是整層失守，這是三條硬規則中最硬的一條 |
| 不打 API、不寫 localStorage、不操作 `window` | 副作用屬於 L2／L1 |
| 不直接呼叫 history、不自己拼 macro | 由 L2 翻譯 event → L1 高階 action |
| 不從 router 讀路由參數 | 路由屬於 L2 |
| 不在內部維護「全域共享」的暫存狀態 | 跨元件狀態走 L2 props |

> 例外：純元件本地 UI 狀態（hover、自己的展開／收合、輸入框未送出文字、拖移分隔線時的暫態比例）可以用 `ref` 留在 L3。判斷標準是「離開這個元件就不再需要」。

## 2. 三條硬規則（再強調一次）

```
L1 基礎層   : Pinia stores、型別、FlowEngine、history、graph utility
L2 容器層   : 消費 store、主畫面 layout、互動，對 L3 開 props/events
L3 UI 元件層 : 純展示元件，不 import 任何 store，只看 props 發 events
```

1. **L3 禁止 `import { useXxxStore }`** — PR review 第一個檢查項目。
2. L1 不寫真實 UI。
3. L2 不做純視覺樣式調整。

## 3. L3 元件標準寫法（Dumb Component 模式）

每個 L3 元件遵守同一個骨架。下例為一個簡化的設備卡片：

```vue
<!-- src/components/DeviceToolbar/DeviceCard.vue -->
<script setup lang="ts">
interface Props {
  deviceId: string
  name: string
  iconUrl: string
  selected?: boolean
  disabled?: boolean
}

interface Emits {
  (e: 'pick', deviceId: string): void
}

const props = withDefaults(defineProps<Props>(), {
  selected: false,
  disabled: false,
})
const emit = defineEmits<Emits>()

const onClick = () => {
  if (props.disabled) return
  emit('pick', props.deviceId)
}
</script>

<template>
  <button
    class="flex flex-col items-center p-2 rounded-md border"
    :class="[
      selected ? 'border-primary bg-primary/10' : 'border-neutral-300',
      disabled && 'opacity-50 cursor-not-allowed',
    ]"
    @click="onClick"
  >
    <img :src="iconUrl" :alt="name" class="w-10 h-10" />
    <span class="text-xs mt-1">{{ name }}</span>
  </button>
</template>
```

### 共同約定

| 項目 | 約定 |
|---|---|
| 語言 | `<script setup lang="ts">` |
| Props | 一律 `defineProps<Props>()` + interface；不接收 store 物件、不接收 Pinia getter |
| Emits | 一律 `defineEmits<Emits>()` + 具名 event |
| 樣式 | Tailwind v4 utility class 為主；複合元件直接使用 Nuxt UI v3 |
| i18n | 顯示文字暫時用繁體中文寫死；後續若做 i18n，由 L2 注入字典 |
| 副作用 | 禁止 `onMounted` 內打 API；本地 `ref` 與 `computed` 自由使用 |

### 元件資料夾命名慣例

- 每個元件對應一個 PascalCase 資料夾
- 主元件用 `Index.vue` 命名
- 該元件的子元件用 PascalCase 平鋪在同一資料夾下（不要再開 `nodes/` 之類的次層）
- 範例：`src/components/InfoPanel/Index.vue`（主）、`src/components/InfoPanel/RecipeListTab.vue`（子）

## 4. 與 L2 的介面協定

L3 元件的介面由 L2 主責人「先開規格、後實作」。流程如下：

1. L2 主責人在自己的 markdown 中列出「我需要這個元件、它的 props 是什麼、會 emit 什麼」
2. L3 主責人 review props/events 介面是否合理、有無漏項
3. 雙方在 PR 描述 / GitHub Issue 中確認後，L3 建立 component skeleton 與 Storybook
4. L2 將容器層接線到該元件，L3 視需要微調樣式

### 目前狀態（重要）

- **L1 上游已就緒**：editorStore（含 nodes / edges 與 8 個高階 actions）、historyStore、canvasStore、validationStore、flowStore、selectionStore 都已完成；useValidation / useFlowEngine / useShortcuts composables 也都已串接。
- **L2 容器層尚未開工**：`Canvas/Index.vue`、`InfoPanel/Index.vue` 等 L2 容器元件還沒寫；harry / toby 尚未動工。
- 因此 L3 各元件目前能做的是：先以 mock data 寫純展示版本與 Storybook 範例；正式的 props / emits 介面要等 L2 開規格時才會凍結。
- L3 元件**不會直接 import L1 的型別**（例如 `FactoryNode` / `Alert` / `RecipeDef`）。L2 會把這些 L1 型別攤平為 plain DTO（預計放在 `src/types/ui/`）再以 props 餵進 L3。

### L1 已存在型別 → L3 對應 DTO 對照（由 L2 攤平）

| L1 型別（已存在） | L3 對應 DTO 範例（由 L2 維護） |
|---|---|
| `FactoryNode` / `FactoryNodeData` | `DeviceInfo` / `PlacedDeviceInfo` |
| `Machine`（`src/types/machine`） | `DeviceInfo`（label, size, ports, power, recipes 等） |
| `RecipeDef` | `RecipeInfo` |
| `Alert` / `AlertLevel` | `AlertItem` |
| `EdgeFlow` / `ItemSummary` | `ItemRow` / `EdgeFlowInfo` |

> 註：實際 store 用 `FactoryNode` / `FactoryEdge`（Vue Flow 型別包裝），並沒有 `PlacedDevice` / `Connection` 這類型別。L3 不需要感知這層，看 plain DTO 即可。

### 介面變更協調

任何 props / emits 簽名變更，由提案的一方在 PR 標題標 `[L2/L3 interface]`，並 mention 另一側的主責人。型別檔（若放在 `src/types/ui/`）統一由 L2 維護，L3 只能 import。

## 5. 工作流程

```
[L2 開 props/events 規格]
        ↓
[L3 建立元件 + Storybook 範例]
        ↓
[L3 用 mock data 驗收靜態畫面]
        ↓
[L2 接線真實 store 資料]
        ↓
[L3 微調樣式 / 視覺細節]
```

驗收標準：開發者打開 Storybook（或 `/dev/components` 預覽頁），不啟動任何 store，就能看到元件在不同 props 組合下的所有狀態。

## 6. 共用樣式規範

- **顏色**：盡量沿用 Nuxt UI 的 semantic token（`primary` / `error` / `warning` / `success` / `neutral`）。自訂顏色（如效率分級的綠／黃／橘／灰）統一寫在 `src/assets/styles/tokens.css`。
- **效率顏色分級**（CR-04 / CR-05 共用）：
  | 等級 | 顏色 token | Tailwind 對照 |
  |---|---|---|
  | 100% | `efficiency-green` | `bg-green-500` |
  | 75~99% | `efficiency-yellow` | `bg-yellow-500` |
  | 1~74% | `efficiency-orange` | `bg-orange-500` |
  | 0% / N/A | `efficiency-gray` | `bg-neutral-400` |
- **間距**：以 Tailwind 預設 spacing scale 為主，避免硬寫 px。
- **字級**：標題 `text-base` / 內文 `text-sm` / 補充說明 `text-xs`。

## 8. PR Review 檢查清單（L3）

審 L3 PR 時逐項確認：

- [ ] 沒有 `import { useXxxStore }`、沒有 `import ... from '@/stores/...'`
- [ ] 沒有 `import` 到 `@/lib/flowEngine`、`@/lib/history` 等 L1 模組
- [ ] Props / Emits 都有 TypeScript interface
- [ ] 元件沒有打 API、沒有讀 `localStorage`
- [ ] 有對應的 Storybook 範例或 `/dev/components/*` 預覽頁
- [ ] 樣式使用 Tailwind / Nuxt UI，沒有未經討論的硬編碼顏色
