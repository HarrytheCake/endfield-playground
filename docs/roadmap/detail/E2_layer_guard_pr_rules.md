## 1. 背景與動機

git 分析顯示主編 144 筆提交裡約 33 筆是 merge，加上 spec、plan-history、幫別人 format 與搬路徑——**整合已經佔滿他每週 3–5 小時的全部**。這是全案最脆弱的一點：唯一的合入者同時也是唯一的守門者，而且他的時間已經沒有餘裕。

本項要做的不是增加規範，而是**把已經在做的守門動作寫成可預期的規則**，讓多數退回可以在提交前就避免，從而把主編的時間從「修別人的路徑」還給「判斷該不該合」。

## 2. 團隊看得到什麼

每個人知道什麼樣的 PR 會被退回、什麼時候會被 review、卡住多久算正常。

## 4. 技術決策

### 4.1 自動退回清單（不需討論，直接退）

| # | 情況 | 為什麼 |
|---|------|--------|
| 1 | 用 GitHub 網頁「Add files via upload」交檔 | 路徑與歷史都會亂 |
| 2 | 檔名帶版本或日期（`Xxx.vue0811`、`Xxx_final.vue`） | 版本歸 git 管 |
| 3 | 檔案在 repo 根目錄或 `docs/<自己>/` 當程式碼 | 不是原始碼位置 |
| 4 | L3 元件 import store 或 `src/data/*` | 分層硬規則 |
| 5 | L2 出現 `nodes.push` 或 `historyStore.execute` | 唯一寫入點規則 |
| 6 | detector import Vue／Pinia | 純函式規則 |
| 7 | 手改 `src/data/*.ts` | 產物，見 [E1](./E1_data_codegen_ops.md) |
| 8 | AI 暫存大檔（`opus.ts`／`sonnet.ts` 之類）進正式樹 | 不可 review |
| 9 | `pnpm type-check`／`lint-check`／`format-check`／`test` 未過 | 基本門檻 |
| 10 | PR 涵蓋範圍超出工單「交哪個檔」 | 一週一塊規則 |

退回時只需引用編號，不需要每次重寫理由。這是為主編節省時間的核心設計。

### 4.2 待審上限與排序

| 規則 | 內容 |
|------|------|
| 同時待審 PR | **≤ 3** |
| 排序 | 擋門檻的必要工項 → 純函式／資料 → 視覺 → 教學型 |
| 超出上限 | 後到的標「延壓」，不計為未完成（見 [A4](./A4_weekly_cadence_gate.md) §4.3） |

### 4.3 Breaking 變更流程

本輪已知會動到 L1 簽名的有：[C2](./C2_add_connection_contract.md)（`addConnection` 加檢查）、[C5](./C5_source_primary_output.md)（新增 `setNodePrimaryOutput`）、[D4](./D4_blueprint_json_io.md)（新增 `loadBlueprint`）、[B5](./B5_delete_single_device.md)（`removeDevices` 連帶移除）。

| 步驟 | 動作 |
|------|------|
| 1 | 在 PR 標題標 `[Breaking]`，說明影響哪些呼叫端 |
| 2 | **先改 L1**，合入 |
| 3 | 下一週才改 L2 |
| 4 | **同一週不逼 L3 跟版** |

### 4.4 開工前一句話

對「與 AI 討論後直接推 PR」的成員（toby、azure、MBD），工單要求開工前先回報一句「我要改的是哪個檔」。這一句能擋掉最貴的一種浪費：整個 PR 方向錯誤，review 時才發現。

### 4.5 單點依賴的備援

主編是唯一合入者。備援方案（依序）：

1. **延壓**：非門檻工項的 PR 可等下週，不計失敗
2. **暫代 review**：純函式與資料類 PR，主編不可用時由 aaaaa review，主編事後追認
3. **不做的事**：不開放自行合入 master
